1. Introduction to Razor Pages

Razor Pages is a page-focused framework introduced in ASP.NET Core 2.0 for building dynamic, data-driven web applications. It offers a simpler alternative to the traditional MVC pattern while maintaining all the powerful features of ASP.NET Core.

What are Razor Pages?

Razor Pages are .cshtml files that contain HTML markup and C# code using Razor syntax. Each page works as a self-contained endpoint with its view and logic together, making it easier to reason about functionality.

Page-Focused Development

Each Razor Page is a self-contained endpoint, simplifying the development of page-specific functionality.

Built-in Support

Includes built-in support for common tasks like routing, model binding, and form validation.

Separation of Concerns

Clean separation between UI (Razor markup) and business logic (PageModel classes).

Project Structure

MyRazorApp/
 ├── Pages/                  # Contains Razor Pages
 │   ├── _ViewImports.cshtml # Common imports and directives
 │   ├── _ViewStart.cshtml   # Common view initialization
 │   ├── _Layout.cshtml      # Shared layout template
 │   ├── Index.cshtml        # Homepage
 │   └── Index.cshtml.cs     # PageModel for Homepage
 ├── wwwroot/                # Static files (CSS, JS, images)
 ├── Program.cs              # App startup and configuration
 └── appsettings.json        # Configuration settings

    }

Basic Anatomy of a Razor Page

@page directive

Makes the .cshtml file handle requests directly

@model directive

Specifies the PageModel class for this page

HTML Markup

Standard HTML with Razor syntax integration

Razor Syntax

@-prefixed C# code embedded in HTML

PageModel Class

Contains the page's logic and data

Handler Methods

OnGet(), OnPost(), etc. to process requests

Why Razor Pages?

Razor Pages was created to simplify web development in ASP.NET Core and provide a more intuitive page-based programming model that's easier to learn, especially for developers new to ASP.NET Core.

Key Takeaway

Razor Pages offers a more straightforward approach to building web applications by combining the view (HTML) and controller logic (C# code) into a single file or paired files, making it easier to understand the relationship between the UI and its behavior.

2. Razor Pages vs MVC

Both Razor Pages and MVC are patterns for building web applications in ASP.NET Core. Understanding their differences helps you choose the right approach for your project.

Feature Razor Pages MVC
Architecture Page-centric, with view and controller logic combined Separates Models, Views, and Controllers into different components
File Organization CSHTML file and PageModel class paired together Controllers, Views, and Models in separate directories
URL Routing File-based routing (by default) Convention-based and attribute routing
Entry Point The Razor Page itself with @page directive Controller action methods
Best For Simpler, page-focused scenarios Complex applications with many shared components
Learning Curve Generally easier to learn Steeper learning curve

When to Choose Each Pattern

When to Choose Razor Pages

  • For smaller applications
  • When you need a page-focused development approach
  • For simpler CRUD operations
  • When your pages have distinct functionality
  • For beginners learning ASP.NET Core

When to Choose MVC

  • For larger, more complex applications
  • When you need fine-grained control over routing
  • For high reusability of controllers and views
  • When building API endpoints alongside your views
  • If your team is already familiar with MVC

Important Note

Razor Pages and MVC are not mutually exclusive. You can use both in the same ASP.NET Core application! Choose the pattern that best fits each specific part of your application.

3. Page Model

The PageModel class is a core concept in Razor Pages that separates the page's logic from its markup. It encapsulates the data and functionality needed by the Razor Page.

What is a PageModel?

A PageModel class provides a clean way to separate the business logic from the presentation logic in a Razor Page. Each .cshtml file can have an associated PageModel class that typically shares the same name but with a .cs extension (e.g., Index.cshtml and Index.cshtml.cs).

PageModel Structure

ExampleModel.cs
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.RazorPages;

namespace MyApp.Pages
{
    public class ExampleModel : PageModel
    {
        // Properties to hold page data
        public string Message { get; set; } = "";
        public List<string> Items { get; set; } = new();
        
        // Handler method for GET requests
        public void OnGet()
        {
            Message = "Page loaded with GET";
            Items = new List<string> { "Item 1", "Item 2", "Item 3" };
        }
        
        // Handler method for POST requests
        public IActionResult OnPost()
        {
            // Process form submission...
            return RedirectToPage();
        }
    }
}

Key Components of a PageModel

PageModel Inheritance

All PageModel classes inherit from the PageModel base class, which provides access to common properties and methods needed for request processing.

Properties

Public properties defined in the PageModel are accessible in the corresponding Razor Page via the @Model directive. These properties can be used to pass data from the PageModel to the view.

Handler Methods

Methods that respond to HTTP requests. Common handlers include OnGet() for GET requests and OnPost() for POST requests.

Helper Properties

The PageModel base class provides several helper properties like HttpContext, ModelState, Request, Response, etc.

Helper Properties Provided by PageModel

  • HttpContext - Access to the current HTTP context
  • ModelState - Validation state of submitted form values
  • Request - The current HTTP request
  • Response - The HTTP response to be sent
  • RouteData - The current route data
  • TempData - Temporary data that persists for a single request
  • User - The current user principal

PageModel Lifecycle

1. Constructor

PageModel constructor executes, often used for dependency injection

Example:
public ExampleModel(IExampleService service)
{
    _service = service;
}

2. Model Binding

Properties marked with [BindProperty] are populated from request data

Example:
[BindProperty]
public string Name { get; set; } = "";

3. Handler Execution

The appropriate handler method (OnGet, OnPost, etc.) is executed

Example:
public void OnGet()
{
    Message = "Hello, World!";
}

4. Result Processing

Handler method's result is processed (e.g., rendering the page)

Example:
public IActionResult OnPost()
{
    if (!ModelState.IsValid)
        return Page();
    
    return RedirectToPage("/Success");
}

5. Page Rendering

The .cshtml page is rendered with access to the PageModel's properties

Example:
<h1>@Model.Message</h1>

<ul>
    @foreach (var item in Model.Items)
    {
        <li>@item</li>
    }
</ul>

Using the BindProperty Attribute

ContactModel.cs
public class ContactModel : PageModel
{
    [BindProperty]
    public string Name { get; set; } = "";
    
    [BindProperty]
    public string Email { get; set; } = "";
    
    [BindProperty]
    public string Message { get; set; } = "";
    
    public string SubmissionResult { get; set; } = "";
    
    public void OnGet()
    {
        // Initialize the page
    }
    
    public void OnPost()
    {
        // Name, Email, and Message properties are automatically
        // populated from form values due to [BindProperty]
        
        if (ModelState.IsValid)
        {
            SubmissionResult = $"Thank you, {Name}! We've received your message.";
        }
    }
}

Best Practice

For clean separation of concerns, keep data manipulation logic in services and inject these services into your PageModel. This makes your code more testable and maintainable.

4. Routing

Routing in Razor Pages determines how URLs map to physical pages in your application. By default, Razor Pages uses a file-based routing system, which makes it intuitive and straightforward.

Routing Basics

In Razor Pages, the route for a page is determined by its location in the file system, relative to the Pages folder. For example, a file at Pages/Products/Details.cshtml would be accessed via the URL /Products/Details.

Default Routing

File Location URL
Pages/Index.cshtml /
Pages/About.cshtml /About
Pages/Products/Index.cshtml /Products
Pages/Products/Detail.cshtml /Products/Detail

Index Pages

Files named Index.cshtml act as the default page for a directory. For example, /Products would route to Pages/Products/Index.cshtml.

Route Parameters

You can add route parameters to your Razor Pages by modifying the @page directive. This allows you to capture values from the URL.

ProductDetail.cshtml
ProductDetail.cshtml.cs
ProductDetail.cshtml
@page "{id:int}"
@model ProductDetailModel

<h1>Product Details</h1>
<p>Viewing product ID: @Model.ProductId</p>
ProductDetail.cshtml.cs
public class ProductDetailModel : PageModel
{
    public int ProductId { get; set; }
    
    public void OnGet(int id)
    {
        ProductId = id;
        // Load product details using the ID
    }
}

Route Parameter Constraints

ASP.NET Core supports various constraints for route parameters:

int

Parameter must be an integer

Example:
@page "{id:int}"

bool

Parameter must be a boolean

Example:
@page "{active:bool}"

datetime

Parameter must be a valid DateTime

Example:
@page "{date:datetime}"

decimal

Parameter must be a decimal value

Example:
@page "{price:decimal}"

guid

Parameter must be a valid GUID

Example:
@page "{id:guid}"

required

Parameter is required

Example:
@page "{name:required}"

minlength / maxlength

Parameter must have a min/max length

Example:
@page "{code:minlength(6)}"

length

Parameter must have a specific length range

Example:
@page "{code:length(6,10)}"

range

Parameter must be within the range

Example:
@page "{quantity:range(1,100)}"

alpha

Parameter must consist of alphabetical characters

Example:
@page "{name:alpha}"

regex

Parameter must match the regular expression

Example:
@page "{sku:regex(^[A-Z]\\d{{3}}$)}"

Optional Parameters

You can make route parameters optional by adding a question mark after the parameter name:

ProductDetail.cshtml
ProductDetail.cshtml.cs
ProductDetail.cshtml
@page "{id:int?}"
@model ProductDetailModel
ProductDetail.cshtml.cs
public void OnGet(int? id)
{
    if (id.HasValue)
    {
        // Load specific product
        ProductId = id.Value;
    }
    else
    {
        // Handle case when no ID is provided
        ProductId = 0;
    }
}

Multiple Route Templates

Razor Pages allows you to define multiple route templates for a single page:

@page
@page "{id:int}"
@model ProductDetailModel

This configuration allows the page to be accessed both with and without an ID parameter.

Custom Routes

You can customize the route for a page by adding a different pattern to the @page directive: 

@page "/product-details/{id:int}"
@model ProductDetailModel

Now, instead of accessing the page at /Products/Detail/1, you would use /product-details/1.

}

Areas in Razor Pages

For larger applications, you can organize your pages into Areas. An Area is a functional grouping of Razor Pages. For example, you might have an "Admin" area for administrative pages and a "Shop" area for customer-facing pages.

To use Areas, create an Areas folder in your project, then add Area folders under it:

MyApp/
 ├── Areas/
 │   ├── Admin/
 │   │   └── Pages/
 │   │       ├── _ViewImports.cshtml
 │   │       ├── _ViewStart.cshtml
 │   │       └── Index.cshtml
 │   └── Shop/
 │       └── Pages/
 │           ├── _ViewImports.cshtml
 │           ├── _ViewStart.cshtml
 │           └── Index.cshtml
 └── Pages/
     └── Index.cshtml

The URL for Areas/Admin/Pages/Index.cshtml would be /Admin.

5. Handler Methods

Handler methods in Razor Pages are responsible for processing HTTP requests. They define what happens when a user visits a page or submits a form.

What are Handler Methods?

Handler methods are methods in the PageModel class that respond to HTTP requests. They follow a naming convention that begins with "On" followed by the HTTP method name (Get, Post, etc.).

Basic Handler Methods

IndexModel.cs
public class IndexModel : PageModel
{
    public string Message { get; set; } = "";
    
    // Handles GET requests
    public void OnGet()
    {
        Message = "This page was loaded with a GET request.";
    }
    
    // Handles POST requests
    public void OnPost()
    {
        Message = "This page was loaded with a POST request.";
    }
}

Handler Method Types

Synchronous Handlers

void OnGet()
void OnPost()
void OnPut()
void OnDelete()

Simple handlers that execute synchronously. They implicitly return a PageResult.

Asynchronous Handlers

Task OnGetAsync()
Task OnPostAsync()
Task OnPutAsync()
Task OnDeleteAsync()

Handlers that execute asynchronously. Useful for I/O operations like database or API calls.

Handlers with Return Types

IActionResult OnGet()
Task<IActionResult> OnPostAsync()
RedirectToPageResult OnPost()

Handlers that return specific action results to control response behavior.

Named Handler Methods

Named handlers allow you to handle multiple actions within a single page. They follow the naming convention of "On[HttpMethod][HandlerName]".

ProductModel.cs
Products.cshtml
ProductModel.cs
public class ProductModel : PageModel
{
    public List<Product> Products { get; set; } = new();
    
    public void OnGet()
    {
        // Load products
        LoadProducts();
    }
    
    // Named handler for product deletion
    public IActionResult OnPostDelete(int id)
    {
        // Delete product with the given id
        DeleteProduct(id);
        
        return RedirectToPage();
    }
    
    // Named handler for adding a product to cart
    public IActionResult OnPostAddToCart(int id)
    {
        // Add product to cart
        AddToCart(id);
        
        return RedirectToPage();
    }
    
    private void LoadProducts() { /* ... */ }
    private void DeleteProduct(int id) { /* ... */ }
    private void AddToCart(int id) { /* ... */ }
}

</form>

Handler Method Parameters

Handler methods can accept parameters that are automatically bound from the request:

GET with Query String

public void OnGet(int id, string category)
{
    // 'id' and 'category' are bound from query string
    // e.g., ?id=5&category=electronics
}

POST with Form Data

public void OnPost(string name, string email)
{
    // 'name' and 'email' are bound from form fields
}

Return Types

Page

Returns the current page. This is the default behavior when a handler method returns void. 

public IActionResult OnGet()
{
    return Page();
}

RedirectToPage

Redirects to another page within the application.

public IActionResult OnPost()
{
    // Redirect to the About page
    return RedirectToPage("About");
    
    // Redirect to the About page with parameters
    return RedirectToPage("About", new { id = 5 });
}

RedirectToAction

Redirects to an action in a controller (useful when mixing Razor Pages and MVC).

public IActionResult OnPost()
{
    return RedirectToAction("Index", "Home");
}

NotFound

Returns a 404 Not Found response.

public IActionResult OnGet(int id)
{
    var item = GetItem(id);
    
    if (item == null)
    {
        return NotFound();
    }
    
    return Page();
}

Content

Returns a plain text or HTML content response.

public IActionResult OnGet()
{
    return Content("Hello, World!");
}

Json

Returns a JSON response.

public IActionResult OnGet()
{
    var data = new { Name = "John", Age = 30 };
    return new JsonResult(data);
}

Best Practices

  • Use asynchronous handlers (OnGetAsync, OnPostAsync) for operations that may take time, such as database queries or HTTP requests
  • Use named handlers to distinguish between different actions on the same page
  • Return specific action results (like RedirectToPage or NotFound) instead of manipulating the response directly
  • Keep handler methods focused on a single responsibility

6. Model Binding

Model binding is the process of extracting values from HTTP requests and mapping them to .NET objects in your Razor Pages application. It simplifies handling form submissions and query parameters.

What is Model Binding?

Model binding automatically maps data from HTTP requests (form posts, query strings, route data) to properties and parameters in your PageModel. This eliminates the need for manually parsing request data.

Model Binding Sources

Form Data

Values from HTML form submissions (application/x-www-form-urlencoded or multipart/form-data).

Route Data

Values from route templates, like {id} in @page "{id:int}".

Query Strings

Values from the query string portion of the URL (e.g., ?id=5&name=John).

Binding to Handler Method Parameters

The simplest form of model binding is binding request data to handler method parameters:

Basic Parameter Binding
public void OnGet(int id, string name)
{
    // id and name are automatically bound from:
    // 1. Route data (if @page includes {id} and {name})
    // 2. Query string parameters (?id=5&name=John)
}

Binding to PageModel Properties

You can bind request data to properties in your PageModel using the [BindProperty] attribute:

ContactModel.cs
public class ContactModel : PageModel
{
    [BindProperty]
    public string Name { get; set; } = "";
    
    [BindProperty]
    public string Email { get; set; } = "";
    
    [BindProperty]
    public string Message { get; set; } = "";
    
    public string SubmissionResult { get; set; } = "";
    
    public void OnGet()
    {
        // Initialize the page
    }
    
    public void OnPost()
    {
        // Name, Email, and Message are automatically populated
        // from form fields with matching names
    }
}

Note

By default, properties with [BindProperty] are only bound on POST requests. To bind on GET requests as well, use [BindProperty(SupportsGet = true)].

Preventing Over-posting

Over-posting (or mass assignment) is a security vulnerability where an attacker can modify properties they shouldn't have access to. To prevent this, you can:

Use Binding Exclusion

[BindProperty]
[BindNever]
public bool IsAdmin { get; set; }

The [BindNever] attribute prevents binding to the specified property.

Use View Models

Create specific view models that only contain properties the user should be able to modify, then map these to your domain models.

// View model (only properties the user can modify)
public class UserViewModel
{
    public string Name { get; set; }
    public string Email { get; set; }
}

// Domain model (includes sensitive properties)
public class User
{
    public string Name { get; set; }
    public string Email { get; set; }
    public bool IsAdmin { get; set; }
}

Best Practices

  • Use the [BindProperty] attribute to clearly indicate which properties should be bound
  • Use view models to prevent over-posting
  • For GET requests, use the SupportsGet parameter with the [BindProperty] attribute
  • Use validation attributes to ensure bound data meets your requirements

7. Form Validation

Form validation is essential for ensuring user input meets your application's requirements. ASP.NET Core provides a robust validation framework for both client-side and server-side validation.

What is Form Validation?

Form validation is the process of ensuring that user input meets specific criteria before it's processed by your application. ASP.NET Core supports both client-side (browser) and server-side validation.

Server-Side Validation

Server-side validation is implemented using Data Annotations and the ModelState object:

ContactModel.cs
using System.ComponentModel.DataAnnotations;
using Microsoft.AspNetCore.Mvc;
using Microsoft.AspNetCore.Mvc.RazorPages;

public class ContactModel : PageModel
{
    [BindProperty]
    [Required(ErrorMessage = "Please enter your name")]
    [StringLength(100, MinimumLength = 2)]
    public string Name { get; set; } = "";
    
    [BindProperty]
    [Required(ErrorMessage = "Please enter your email")]
    [EmailAddress(ErrorMessage = "Please enter a valid email address")]
    public string Email { get; set; } = "";
    
    [BindProperty]
    [Required(ErrorMessage = "Please enter a message")]
    [StringLength(1000, MinimumLength = 10, ErrorMessage = "Message must be between 10 and 1000 characters")]
    public string Message { get; set; } = "";
    
    public string SubmissionResult { get; set; } = "";
    
    public void OnGet()
    {
        // Initialize the page
    }
    
    public IActionResult OnPost()
    {
        if (!ModelState.IsValid)
        {
            // Return the page with validation errors
            return Page();
        }
        
        // Process the valid form submission
        SubmissionResult = "Thank you for your message!";
        
        // Clear the form
        ModelState.Clear();
        Name = "";
        Email = "";
        Message = "";
        
        return Page();
    }
}

Custom Validation

You can implement custom validation by creating your own validation attributes or by adding custom validation in the PageModel:

public IActionResult OnPost()
{
    // Custom validation logic
    if (Name.ToLower() == "admin")
    {
        ModelState.AddModelError("Name", "This name is not allowed.");
    }
    
    if (!ModelState.IsValid)
    {
        return Page();
    }
    
    // Process the valid form submission
    return RedirectToPage("ThankYou");
}

You can also create custom validation attributes by inheriting from ValidationAttribute:

using System.ComponentModel.DataAnnotations;

public class NoAdminNameAttribute : ValidationAttribute
{
    protected override ValidationResult IsValid(object value, ValidationContext validationContext)
    {
        if (value == null)
        {
            return ValidationResult.Success;
        }
        
        string name = value.ToString();
        
        if (name.ToLower() == "admin")
        {
            return new ValidationResult("This name is not allowed.");
        }
        
        return ValidationResult.Success;
    }
}

// Usage:
[NoAdminName]
public string Name { get; set; } = "";

Best Practices

  • Always implement server-side validation, as client-side validation can be bypassed
  • Use Data Annotations for simple validation requirements
  • Create custom validation for complex business rules
  • Provide clear, user-friendly error messages
  • Consider using the [Display] attribute to provide user-friendly names for properties

8. Tag Helpers

Tag Helpers enable server-side code to participate in creating and rendering HTML elements in Razor files. They make working with HTML in Razor Pages more intuitive and reduce the amount of code you need to write.

What are Tag Helpers?

Tag Helpers are components that attach to HTML elements in your Razor views and modify them during rendering. They're similar to HTML Helpers but with a syntax that's more familiar to HTML developers. Tag Helper attributes typically start with the prefix "asp-".

Standard HTML

<a href="/Product/Details/5">View Product</a>
→

With Tag Helper

<a asp-page="/Products/Details" asp-route-id="5">
    View Product
</a>

The Tag Helper automatically generates the correct URL based on your application's routing configuration

Common Built-in Tag Helpers

Anchor Tag Helper

Generates links to Razor Pages or MVC controllers/actions.

<a asp-page="/Products/Details" asp-route-id="5">
    View Product
</a>

Form Tag Helper

Generates HTML form elements with proper action URLs.

<form method="post" asp-page-handler="Delete" 
      asp-route-id="@item.Id">
    <button type="submit">Delete</button>
</form>

Input Tag Helper

Generates HTML input elements with proper binding to model properties.

<input asp-for="Product.Name" />

Label Tag Helper

Generates label elements for model properties.

<label asp-for="Product.Name"></label>

Select Tag Helper

Generates select elements for model properties.

<select asp-for="ProductCategory" 
        asp-items="Model.Categories">
    <option value="">Select a category</option>
</select>

Validation Tag Helpers

Displays validation messages for model properties.

<span asp-validation-for="Product.Name"></span>
<div asp-validation-summary="All"></div>

Enabling Tag Helpers

Tag Helpers are enabled in your Razor Pages through the _ViewImports.cshtml file:

@using YourApp
@namespace YourApp.Pages
@addTagHelper *, Microsoft.AspNetCore.Mvc.TagHelpers

The @addTagHelper directive registers the Tag Helpers. The asterisk (*) wildcard specifies that all Tag Helpers in the specified assembly (Microsoft.AspNetCore.Mvc.TagHelpers) are available to all views in your application.

Anchor Tag Helper

The Anchor Tag Helper generates links to Razor Pages or MVC controllers/actions:

<!-- Link to a Razor Page -->
<a asp-page="/Products/Details" asp-route-id="5">View Product</a>

<!-- Link to an MVC controller action -->
<a asp-controller="Products" asp-action="Details" asp-route-id="5">View Product</a>

<!-- Link to current page with a route value -->
<a asp-page="./List" asp-route-category="electronics">Electronics</a>

<!-- Link to a page in an area -->
<a asp-area="Admin" asp-page="/Products/Index">Admin Products</a>

Form Tag Helper

The Form Tag Helper generates HTML form elements with proper action URLs:

<!-- Basic form posting to the current page -->
<form method="post">
    <!-- Form fields -->
    <button type="submit">Submit</button>
</form>

<!-- Form posting to a named handler method -->
<form method="post" asp-page-handler="Delete" asp-route-id="@item.Id">
    <button type="submit">Delete</button>
</form>

<!-- Form posting to another page -->
<form method="post" asp-page="/Account/Login">
    <!-- Form fields -->
    <button type="submit">Login</button>
</form>

Input Tag Helper

The Input Tag Helper generates HTML input elements with proper binding to model properties: 

<!-- Text input for a string property -->
<input asp-for="Product.Name" />

<!-- Renders as: -->
<input type="text" id="Product_Name" name="Product.Name" value="Current Value" />

<!-- Input types are automatically determined based on property type -->
<input asp-for="Product.Price" /> <!-- Renders as type="number" for decimal -->
<input asp-for="Product.AvailableDate" /> <!-- Renders as type="date" for DateTime -->
<input asp-for="Product.InStock" /> <!-- Renders as type="checkbox" for bool -->
<input asp-for="Product.Email" /> <!-- Renders as type="email" with [EmailAddress] -->

The Select Tag Helper generates select elements for model properties:

<!-- Basic select element -->
<select asp-for="ProductCategory" asp-items="Model.Categories">
    <option value="">Select a category</option>
</select>

Validation Tag Helpers display validation messages for model properties:

Creating Custom Tag Helpers

You can create your own Tag Helpers by creating a class that inherits from TagHelper:

using Microsoft.AspNetCore.Razor.TagHelpers;

[HtmlTargetElement("email-link")]
public class EmailLinkTagHelper : TagHelper
{
    public string EmailAddress { get; set; }
    public string LinkText { get; set; }
    
    public override void Process(TagHelperContext context, TagHelperOutput output)
    {
        output.TagName = "a";
        output.Attributes.SetAttribute("href", $"mailto:{EmailAddress}");
        output.Content.SetContent(string.IsNullOrEmpty(LinkText) ? EmailAddress : LinkText);
    }
}

To use this custom Tag Helper, register it in _ViewImports.cshtml:

@addTagHelper *, YourAssemblyName

Then use it in your Razor Pages:

<email-link email-address="[email protected]" link-text="Contact Support"></email-link>

<!-- Renders as: -->
<a href="mailto:[email protected]">Contact Support</a>

Best Practices

  • Use Tag Helpers consistently throughout your application
  • Prefer Tag Helpers over HTML Helpers when possible for better readability
  • Create custom Tag Helpers for repeated HTML patterns in your application
  • Keep Tag Helpers focused on a single responsibility
  • Use proper casing for attributes: Tag Helpers use kebab-case (e.g., email-address) for attributes, which are mapped to PascalCase properties (e.g., EmailAddress)

9. Dependency Injection

Dependency Injection (DI) is a technique for achieving loose coupling between classes and their dependencies. ASP.NET Core has built-in support for DI, which is extensively used in Razor Pages.

What is Dependency Injection?

Dependency Injection is a design pattern where a class receives its dependencies from external sources rather than creating them itself. This makes code more modular, testable, and maintainable by reducing direct dependencies between components.

Without DI (Tight Coupling)

public class ProductPage : PageModel
{
    // Direct dependency, tightly coupled
    private readonly SqlProductRepository _repo = 
        new SqlProductRepository();
    
    public void OnGet()
    {
        Products = _repo.GetAllProducts();
    }
}
→

With DI (Loose Coupling)

public class ProductPage : PageModel
{
    // Interface dependency, loosely coupled
    private readonly IProductRepository _repo;
    
    // Constructor injection
    public ProductPage(IProductRepository repo)
    {
        _repo = repo;
    }
    
    public void OnGet()
    {
        Products = _repo.GetAllProducts();
    }
}

DI in ASP.NET Core

ASP.NET Core includes a built-in DI container that manages the creation and lifetime of application services. Services are registered in the Program.cs file (or Startup.cs in older versions):

var builder = WebApplication.CreateBuilder(args);

// Add services to the container
builder.Services.AddRazorPages();

// Register application services
builder.Services.AddScoped<IProductService, ProductService>();
builder.Services.AddSingleton<IAppSettings, AppSettings>();
builder.Services.AddTransient<IEmailSender, EmailSender>();

var app = builder.Build();

// ... Configure middleware ...

Service Lifetimes

Transient

AddTransient<TService, TImplementation>()

Transient services are created each time they're requested from the service container. This lifetime is best for lightweight, stateless services.

Example:
builder.Services.AddTransient<IEmailSender, EmailSender>();

Scoped

AddScoped<TService, TImplementation>()

Scoped services are created once per client request (connection). This is commonly used for services that need to maintain state within a request, like database contexts.

Example:
builder.Services.AddScoped<IProductService, ProductService>();

Singleton

AddSingleton<TService, TImplementation>()

Singleton services are created the first time they're requested and then reused for all subsequent requests for the lifetime of the application. This is suitable for services that maintain state across requests.

Example:
builder.Services.AddSingleton<IAppSettings, AppSettings>();

Using DI in Razor Pages

You can inject services into your PageModel classes through constructor injection:

public class ProductsModel : PageModel
{
    private readonly IProductService _productService;
    private readonly ILogger<ProductsModel> _logger;
    
    public List<Product> Products { get; set; } = new();
    
    // Constructor injection
    public ProductsModel(IProductService productService, ILogger<ProductsModel> logger)
    {
        _productService = productService;
        _logger = logger;
    }
    
    public async Task OnGetAsync()
    {
        try
        {
            Products = await _productService.GetAllProductsAsync();
            _logger.LogInformation("Retrieved {Count} products", Products.Count);
        }
        catch (Exception ex)
        {
            _logger.LogError(ex, "Error retrieving products");
            Products = new List<Product>();
        }
    }
}

Creating Services

A typical service consists of an interface and its implementation:

public interface IProductService
{
    Task<List<Product>> GetAllProductsAsync();
    Task<Product> GetProductByIdAsync(int id);
    Task<int> CreateProductAsync(Product product);
    Task UpdateProductAsync(Product product);
    Task DeleteProductAsync(int id);
}
public class ProductService : IProductService
{
    private readonly ApplicationDbContext _dbContext;
    
    // Constructor injection
    public ProductService(ApplicationDbContext dbContext)
    {
        _dbContext = dbContext;
    }
    
    public async Task<List<Product>> GetAllProductsAsync()
    {
        return await _dbContext.Products.ToListAsync();
    }
    
    public async Task<Product> GetProductByIdAsync(int id)
    {
        return await _dbContext.Products.FindAsync(id);
    }
    
    public async Task<int> CreateProductAsync(Product product)
    {
        _dbContext.Products.Add(product);
        await _dbContext.SaveChangesAsync();
        return product.Id;
    }
    
    public async Task UpdateProductAsync(Product product)
    {
        _dbContext.Products.Update(product);
        await _dbContext.SaveChangesAsync();
    }
    
    public async Task DeleteProductAsync(int id)
    {
        var product = await _dbContext.Products.FindAsync(id);
        if (product != null)
        {
            _dbContext.Products.Remove(product);
            await _dbContext.SaveChangesAsync();
        }
    }
}

Benefits of DI

Testability

DI makes unit testing easier by allowing you to substitute real services with mock implementations.

Flexibility

You can change implementations without changing the code that uses them.

Maintainability

Components have well-defined interfaces, making the system easier to maintain and evolve.

DI Best Practices

  • Follow the Dependency Inversion Principle: Depend on abstractions (interfaces) rather than concrete implementations
  • Use the appropriate service lifetime for your services
  • Keep services focused on a single responsibility
  • Avoid service locator pattern; prefer constructor injection
  • Don't inject services you don't need
  • Be cautious when using singleton services that maintain state or have dependencies on scoped services

10. View Components

View Components in ASP.NET Core are similar to partial views, but with more power and flexibility. They allow you to create reusable UI components that can include both rendering logic and business logic.

What are View Components?

View Components are self-contained components that render chunks of content in your Razor Pages. Unlike partial views, View Components:

  • Have their own lifecycle
  • Can execute business logic
  • Can have parameters and dependencies injected
  • Are not dependent on model binding

Use Cases for View Components

  • Dynamic navigation menus
  • Shopping cart summary
  • Login panels
  • Sidebar widgets
  • Notification systems
  • Tag clouds

Creating a View Component

A View Component consists of two parts:

  1. A class that derives from ViewComponent
  2. A view file that renders the component's output
ShoppingCartSummaryViewComponent.cs
using Microsoft.AspNetCore.Mvc;

public class ShoppingCartSummaryViewComponent : ViewComponent
{
    private readonly IShoppingCartService _cartService;
    
    public ShoppingCartSummaryViewComponent(IShoppingCartService cartService)
    {
        _cartService = cartService;
    }
    
    public async Task<IViewComponentResult> InvokeAsync()
    {
        var items = await _cartService.GetCartItemsAsync(HttpContext.User);
        
        return View(new ShoppingCartViewModel
        {
            ItemCount = items.Count,
            TotalAmount = items.Sum(i => i.Price * i.Quantity)
        });
    }
}

public class ShoppingCartViewModel
{
    public int ItemCount { get; set; }
    public decimal TotalAmount { get; set; }
}

The view file should be placed in one of the following locations:

  • /Pages/Components/ShoppingCartSummary/Default.cshtml
  • /Views/Shared/Components/ShoppingCartSummary/Default.cshtml
Default.cshtml
@model ShoppingCartViewModel

<div class="cart-summary">
    <i class="fas fa-shopping-cart"></i>
    <span class="badge">@Model.ItemCount</span>
    <span class="total">@Model.TotalAmount.ToString("C")</span>
</div>
